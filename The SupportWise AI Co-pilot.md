# The "SupportWise" AI Co-pilot

## Introduction

The AI Co-pilot for Zendesk enables users to query and analyze their support data through natural language instead of manual dashboards or SQL. It combines a fast analytical backend for metric-based questions with a retrieval-augmented generation (RAG) pipeline for deeper insights into customer feedback. Simple queries are handled through parameterized SQL generated by a small LLM, while complex “why” questions use Qdrant and a larger LLM for semantic analysis. The system is designed to be fast, secure, and scalable, providing an intuitive, chat-based interface for business intelligence.

## 1. System Architecture Overview

The system starts with a Zendesk ingestion layer written in Python that performs an initial backfill and then keeps the dataset fresh via the Zendesk API and webhooks. Ingestion normalizes the JSON payloads, applies basic PII redaction, and lands raw and curated data in a lake format. From there, a SQL-first analytics layer (backed by a columnar OLAP engine such as ClickHouse) exposes modeled facts and dimensions plus materialized pre-aggregations for speed. In parallel, a vector service built on Qdrant stores embeddings for ticket comments, along with metadata like date, priority, and product area to enable filtered semantic retrieval.
On top of these stores sits an orchestrator implemented with FastAPI and served by Uvicorn. The orchestrator routes each chat query: for metric questions it uses a small LLM to translate natural language into parameterized SQL against the OLAP layer, validates and executes the query, and returns numbers or a chart; for “why” questions it extracts scope (time and filters), retrieves relevant comments from Qdrant, and asks a larger LLM to produce an evidence-grounded summary. Chart images are rendered server-side with Matplotlib. Celery workers, with Redis as broker/result backend, execute heavy or scheduled jobs (e.g., weekly reports). Redis also caches hot results and chart artifacts. Security is enforced end-to-end with OIDC for authn, RLS/CLS in the warehouse, strict SQL validation in the orchestrator, and audit logging and observability (OpenTelemetry/Prometheus) across components.

## 2. Data Flow Description

Zendesk data flows into the platform through Python workers that call the Zendesk API and receive webhook events. Raw payloads are sanitized and written to lake storage, then transformed into analytics-ready tables. dbt materializes the core models (tickets and comments) and generates pre-aggregations such as daily ticket counts by priority. In parallel, comment text is chunked and embedded; vectors and their metadata are inserted into Qdrant, and ML pipelines compute sentiment/topics/entities that are stored both in the warehouse and as payload fields in Qdrant for filterable retrieval. When a user asks a metric question in chat, the orchestrator uses a small LLM to compile a parameterized SQL plan against the modeled schema, validates it (SELECT-only, allow-listed columns, required time window), executes it on the OLAP layer, and returns a KPI, table, or a chart rendered by Matplotlib. For explanatory questions, the orchestrator resolves time and filter scope, queries Qdrant for the top-K semantically similar comments constrained by that scope, optionally joins in the precomputed ML signals, and prompts a larger LLM to synthesize a concise answer with ticket-level citations. If a result should be saved or scheduled, the orchestrator persists the report definition (SQL, ChartSpec, and parameter template) and Celery runs it on schedule, caching both data and chart artifacts in Redis for fast re-display.

## 3. Technology Choices

For ingestion, Python plus the Zendesk API and webhooks provide reliable control over backfills, incremental sync, and custom redaction logic. The analytics store is a SQL OLAP engine such as ClickHouse because it delivers sub-second aggregates and cost-efficient materialized views at scale. Modeling and transformation are handled by dbt to version business logic, add tests, and document metrics and dimensions. Qdrant is the vector database because it offers fast approximate nearest-neighbor search with native metadata filters, which is ideal for “retrieve comments about feature X last month with priority high.” Embeddings come from a provider such as OpenAI’s text-embedding-3 models, though the design keeps this pluggable to swap for OSS if needed. The orchestrator is built with FastAPI and Uvicorn for a typed, asynchronous, Python-native service layer. Two LLM tiers are used: a small model for intent classification and NL→SQL planning (low latency and cost), and a larger model for RAG synthesis when explanations are required. Matplotlib renders server-side PNG/SVG to keep visualization deterministic and safe. Celery with Redis covers job orchestration for scheduled/heavy runs, while Redis also serves as a cache for query results and chart images. Governance relies on OIDC for authentication and row/column-level security in the warehouse, with strict SQL validation and parameter binding enforced by the orchestrator, and observability is provided via OpenTelemetry and Prometheus/Grafana.

## 4. Data Schema Structures

At the warehouse layer, the core models are a ticket dimension and a comment fact. The ticket dimension captures identifiers, requester/assignee, status, priority, product area, tags, custom fields, and lifecycle timestamps (created, updated, closed). The comment fact links to tickets and includes author, creation time, visibility, language, and the body text. To support SLA and state evolution, a daily ticket fact records per-day attributes such as whether the ticket was open, current status/priority, first response time, full resolution time, and reopen count. Pre-aggregations store daily and weekly rollups, for example ticket counts grouped by priority and date, so that common questions hit thousands of rows instead of millions. ML signal tables attach sentiment labels/scores and topic assignments to comment IDs, including model version and inference time to maintain lineage. In Qdrant, a comments_embeddings collection stores one vector per comment plus payload metadata fields like ticket_id, date, priority, product_area, language, visibility flag, sentiment label, a source URL, and the embedding model version; these fields enable precise filtering during vector search. The public API exposed by the orchestrator accepts a natural-language query and time zone and returns either a metric response with an interpretation of filters and dates, the validated parameterized SQL used and its result (optionally with a chart URL), or a semantic response that includes scope, a summary, topic drivers with cited ticket IDs and quotes, sentiment distribution, and stated limitations. A separate endpoint accepts a declarative chart specification together with tabular data to produce a static image, and the reports API allows creating a named report with SQL, chart spec, and parameter templates (for example “last_week”), running a report with resolved parameters, and retrieving run artifacts and metadata. Together, these schemas and contracts ensure consistent business definitions, fast and safe execution paths for both metric and explanatory queries, and a clear, auditable interface from raw Zendesk data to end-user answers.

## 5. Detailed Technical Explanations

* **User Experience Flow**: When Brenda types a question like “How many urgent tickets did we get last week?” into the chat, the request first reaches the orchestrator API, which detects her intent and determines whether it is a simple metric query or a more complex analytical question. In this case, the system identifies a metric-type request and forwards it to a small, fast LLM responsible for translating natural language into a parameterized SQL query. The LLM does not access real data; it only uses a predefined semantic catalog of allowed tables and fields. The generated SQL is validated to ensure it only contains SELECT statements, uses allowed columns, includes safe parameters, and defines a time window. Once validated, the query runs on the OLAP database, which holds pre-aggregated data to ensure near-instant responses. The orchestrator then returns the numeric result or a simple visualization if requested. If Brenda’s question were more complex, such as asking for causes or trends, the orchestrator would instead use the vector database and a larger LLM to synthesize the answer.
The main technical challenges here are managing ambiguity in natural language, reducing perceived latency, and ensuring reliability. These are addressed through strict SQL validation, pre-aggregated data, caching, and feedback cues in the chat interface showing the current processing stage.

* **Historical Data Challenges**: Zendesk contains millions of tickets and comments spanning several years, and querying such volumes in real time would normally be slow and costly. To meet Brenda’s expectation of receiving answers within seconds, the system relies on data modeling and pre-aggregation.
Historical ticket and comment data are extracted from Zendesk via APIs and transformed through ETL pipelines into optimized tables for analytics. These transformations produce daily and weekly rollups—such as ticket counts per priority or per product area—that ClickHouse can query efficiently. This reduces latency dramatically because queries operate on a few thousand rows instead of millions. Additionally, recent data is stored in a “hot” layer for quick access, while older data moves to a cheaper “cold” layer. For text-heavy operations, Qdrant enables semantic retrieval with metadata filters rather than full-text scans. Combined with caching of frequent queries, this approach maintains both speed and scalability even as the data grows.

* **Business Data Risks**: Because the AI Co-pilot directly interfaces with Zendesk’s operational data—containing customer communications and business insights—security and governance are essential. If built carelessly, the system could expose private information and allow unauthorized access to sensitive tickets. To prevent this, several layers of protection are applied. All Zendesk data undergoes PII redaction at ingestion. The orchestrator enforces that all SQL generated by the LLM is SELECT-only, parameterized, and constrained to allowed schemas. Row-level and column-level security are active in the database to ensure users only access data relevant to their role. The LLM is isolated from direct data exposure—it only plans queries or summarizes validated results. Outputs from the LLM are further sanitized before display to the user. Finally, authentication and authorization follow an OIDC standard, with encrypted communication channels and detailed audit logging of every query. These controls ensure that the AI Co-pilot remains safe and compliant in a production environment.

* **Complex Business Questions**: Questions like “Why are customers unhappy with our new feature?” require understanding text semantics, not just structured data. Since raw Zendesk data includes ticket fields and comment text but not explicit sentiment, the system uses a hybrid RAG approach. First, an ML pipeline preprocesses all comments, computes sentiment scores and topic tags, and stores them as metadata in the database and Qdrant. When Brenda asks a “why” question, the orchestrator identifies the relevant scope (for example, feature name, priority, and date range) and retrieves the most semantically similar comments from Qdrant based on vector similarity and metadata filters. These results—usually a small set of relevant ticket fragments—are then summarized by a large LLM to produce a human-readable explanation that includes cited ticket IDs and a breakdown of common themes or emotions. If insufficient evidence is found, the system explicitly communicates that limitation rather than hallucinating. This approach allows the AI Co-pilot to transform unstructured feedback into structured insights in a controlled and explainable way.

* **Workflow Efficiency**: Brenda frequently repeats similar tasks, such as generating a weekly ticket report. To eliminate this manual repetition, the system supports persistent and reusable reports. When Brenda generates a chart or query she likes, she can save it as a named report, storing the SQL statement, visualization configuration, and parameter templates (for example, “last_week”). The next time she requests “Run the Weekly Ticket Report”, the orchestrator automatically resolves the date parameters, executes the saved query, regenerates the visualization, and returns the results. Scheduled jobs managed by Celery and Redis can also automate report execution every Monday morning, with results stored as PNGs or CSVs in the system. This design transforms repetitive manual workflows into automated, repeatable processes, saving time and reducing human error.

* **Data Visualization Needs**: Brenda expects not just numerical answers but visualizations she can quickly interpret. When she asks for a bar chart or line chart, the system must translate structured results into an image safely and consistently. This requirement introduces challenges in security, performance, and consistency. To handle it safely, the LLM never executes arbitrary plotting code. Instead, it emits a declarative ChartSpec describing axes, labels, and chart type, which the orchestrator passes to a controlled Python renderer built with Matplotlib. The renderer converts the aggregated SQL data into a static PNG or SVG image that can be displayed in the chat. This process ensures that the visual output is deterministic, reproducible, and secure. To prevent overload, large result sets are downsampled or aggregated before plotting, and rendered images are cached in Redis for quick re-display.

* **Operational Cost Management**: The system must balance fast, inexpensive metric queries with the higher cost of complex semantic analyses. To manage this variability, the orchestrator routes queries based on intent: simple factual questions use pre-aggregated SQL tables and a small, cheap LLM; complex “why” questions use Qdrant retrieval and a large LLM, which is slower and more expensive. Frequent or repeated queries are cached in Redis to minimize recomputation. Batch processes such as embeddings or sentiment updates run incrementally rather than reprocessing the entire dataset. Heavy tasks can be offloaded to asynchronous Celery jobs executed on cheaper compute resources. By separating workloads and applying quotas and rate limits, the system keeps costs predictable while maintaining responsiveness.

* **Technology Evolution**: AI tools evolve rapidly, and models or APIs in use today might be obsolete in a few months. To prevent lock-in and enable adaptation, the architecture separates the model logic behind a Model Gateway abstraction layer. This allows embedding models, LLMs, and even vector databases to be swapped without changing the orchestration logic. All data contracts and SQL schemas are versioned, so breaking changes are easily managed. The system includes observability to detect model drift or provider outages and supports blue/green deployments for safe updates. If a new model offers better performance or cost, it can be integrated by simply updating the model configuration in the gateway. This design ensures long-term resilience and flexibility as the AI ecosystem continues to evolve.
